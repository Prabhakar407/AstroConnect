## C01 — A customer can understand the booking without assistance

Retain the established colours, type family, header/footer and artwork. Reorganize only the booking form's internal information order: **consultation and time → contact/birth details → review, verify email and pay → appointment status**. This is a sequence within one page, not a forced multi-page wizard. On landscape, use readable grouped cards and a compact review summary; on mobile, stack in that same order and keep the next action beside its explanation. No mandatory customer account, extra decorative stepper or automatic scrolling between every input.

1. Preselect a valid service from the link. Show its fee immediately; show “Number of questions” only for Prashna. Changing service resets quantity to one. Navigating to another service while a draft/payment exists must not silently overwrite it; confirm discarding an unpaid draft, and preserve an active checkout.
2. Select a date and one half-hour time. Show “All times are in India Standard Time” and the exact bookable date range. Restrict month navigation to months containing eligible dates. Unknown availability disables choice and offers “Try again”; it is not an empty calendar or a fully booked day.
3. Collect the existing details, not extra marketing/profile questions. Clearly distinguish required fields. Keep birth time/place and notes optional. The current screen requires birth date: preserve that default and enforce it consistently on the server for the new public checkout; changing whether a service needs birth date is a client content decision, not an accidental backend omission.
4. Before requesting email verification, show service, question count if relevant, exact date/start/end in IST, 30-minute length, final fee and cancellation phone. Primary action: “Verify email and continue”. The verification dialog names the address, supports paste/autofill and “Change email”, and explains resend/expiry without using “OTP” as the only label.
5. After successful verification, recheck availability and the acknowledged quote. Reserve only now, not while someone is typing or waiting for a code. If the slot was taken, preserve their details and unconsumed verification proof, say “That time was just booked. Please choose another”, and do not charge. A price change requires a new review/acknowledgement, never an automatic higher charge.
6. Once a hold and provider order are safely bound, show the actual server deadline and “Pay ₹… securely”. Only this deliberate action opens Razorpay. An order already being prepared shows “Preparing secure payment”; it must not tempt another checkout. The timer reflects the existing deadline and never extends it on refresh.
7. Show one main result and one next action. A paid, reserved appointment is “Appointment confirmed”; if its link is still being prepared, say so underneath. A captured payment without a confirmed appointment says “Payment received; appointment needs attention. Please do not pay again” with the studio phone/reference. Never label every database or provider state as a separate step the customer must manage.

Display alongside Prashna's total: “Additional questions during the consultation cost ₹1,100 each, payable at that time.” Question count changes the fee, not the appointment duration. Do not require ten separate question-entry boxes; optional notes are sufficient. A service-page question/inquiry is not a paid consultation.

### Boundary fields and compatibility

- Required public checkout: stable request UUID; separate receipt proof (C03); verified email; full name 2–100 characters; normalized phone 7–15 digits with optional leading `+`; one of the six service IDs; strict integer question count 1–10 (one for other services); exact `YYYY-MM-DD` booking date; a listed `HH:MM` slot; acknowledged catalogue/quote version; structured birth date not in the future. All timestamps are timezone-aware; money is integer paise.
- Optional birth time: valid local `HH:MM`, not silently treated as IST or converted to the customer's current timezone. Birth location: bounded text (proposed limit 200 characters); notes: at most 4,000 characters. “Unknown” is missing, not midnight. Do not infer a birth timezone or generate a chart.
- Recorded booking-input follow-up (2026-09-13): replace the browser-native birth-date field with a paste-friendly, day-first field. Accept `DD-MM-YYYY`, `DD/MM/YYYY`, `DD-MMM-YY`, `DD-MMM-YYYY` and the same month-name forms with slashes, without guessing a different month/day order. Show one simple example, validate clearly, and normalize the accepted value to `YYYY-MM-DD` before it reaches the existing server contract. Replace the browser-native birth-time field with simple hour, minute and AM/PM controls while preserving an explicit unknown/optional state. This is deliberately recorded for a focused input pass rather than mixed into the current layout and availability repair.
- Replace concatenation of phone, birth fields and notes into one 4,000-character `birth_details` string with bounded structured fields. Add compatible storage columns; retain legacy text for existing dummy rows without guessing how to parse it. Do not make every old row satisfy a new public-input rule by inventing dates.
- Map server error codes to individual field messages using field names, never echoing rejected values. Browser and server agree on trimming, required fields, lengths and phone normalization; the browser cannot invent stricter business rules such as rejecting particular digit patterns unless agreed.
- Server quote remains authoritative. Include a version/fingerprint of the displayed quote in the request as an acknowledgement check, not as a trusted price. Freeze the accepted name/amount/quantity/duration on a hold. A retry of an existing hold reads its frozen terms before applying a newer catalogue. Never overwrite historical prices.
- Public metadata endpoints return explicit objects, for example `{services: [...]}`. Services, quote acknowledgement and coordinated policy/availability contracts are now implemented/tested. Full public checkout and review/payment presentation remain unfinished; internal hold acceptance is not a payment integration.

## C02 — Schedule rules mean the same thing everywhere

- Policy/availability now return `server_now`, `first_date`, `last_date`, `timezone`, `duration_minutes`, slot labels and readiness from one database-clock source. Availability includes `date` and a `slots` boolean object; missing storage returns unavailable. The browser uses this horizon, not its device clock, and pauses hidden/idle polling. Local browser checks against real Neon passed with a deliberately wrong year/timezone; actual Vercel behavior remains unproved.
- Today through today +10 calendar dates is inclusive, not ten working days. Use IST across website, database comparisons, payment deadlines, Calendar events and client views. A device in another country sees the same Indian schedule. No changing the timezone of birth details.
- Only starts 10:00, 10:30, 11:00, 11:30, 15:00, 15:30, 16:00, 16:30, 17:00 and 17:30, Monday–Saturday. End time is start +30 minutes. Keep the existing unique `slot_claims.starts_at` plus transaction-scoped schedule lock. At this scale, replacing it with distributed locks adds risk, not value.
- Selection is not reservation. Hold/closure/payment writes acquire the same lock, expire old holds, recheck state and commit atomically. Never call Google, Resend or Razorpay under that lock. Repeated polling cannot prolong a hold.
- Public slots say available/unavailable, never customer names, reasons for absence, holds or phone numbers. Use opaque IDs only in protected contexts. A selected slot can become unavailable between reads; the write is decisive.
- Full-day closure means all business slots on that date. Partial closure covers starts in `[from, until)`; lunch is ignored, not added as bookable time. Reject the entire request if any covered slot is booked, held or already closed. Show precisely which times prevent closure to the authenticated client. Reopening affects only that closure.
- Separate **read** date validation from **mutation** date validation. The client can inspect past booking days/history; they cannot close past dates, alter past appointments or perform a phone cancellation after its start through this flow. A Sunday is already closed for consultations; suppress a redundant “close Sunday” action. Today may contain past appointments: full-day closure must still protect them.
- For today's full-day closure, check the whole day's bookings/holds first; a prior confirmed appointment still prevents closing that whole day. If the day is otherwise eligible, create claims only for not-yet-started business slots. A partial range including past starts is rejected with a clear instruction to choose future times. An all-past/no-remaining range cannot create an empty closure. Test these separately from historical reads.
- Visible pages may refresh on focus and a bounded interval; hidden tabs and long-idle private pages stop polling. Resume with an explicit refresh before writing. A phone's suspended timer is not a clock. Handle midnight, month rollover and out-of-order responses without clearing typed details.

**D10 — approved and verified locally in the first 2026-09-10 preparation slice:** public availability and internal hold creation enforce `starts_at >= server_now + 30 minutes`. Exactly 30 minutes is accepted, one second less rejected. An unchanged internal hold retry preserves its original deadline/quote without restarting notice. Session length and horizon are unchanged. This is not yet a receipt-authorized public checkout; that integration and provider timing remain pending. Ten-minute holds leave preparation time but cannot guarantee recovery during provider outages.

## C03 — Verification, retries and recovery have distinct jobs

**No customer account system.** Email proof allows a specific action; it is not the client's Google login. A request UUID prevents accidental duplication; it is not authorization to read a booking.

Receipt foundations below (creation, digest/expiry, authorized retry and limited status) are implemented with focused tests. Cross-device verified recovery, complete payment/link status and pre-code retry UX remain unfinished:

1. Before the first save/checkout request, generate a UUID and an independent 256-bit random receipt secret with Web Crypto. Keep only those identifiers in tab-scoped `sessionStorage`; do not persist birth details, notes, OTPs or full form contents there. Keep unsubmitted text in page memory. A page refresh before save can lose unsaved text; do not promise otherwise or silently store sensitive drafts.
2. Send the secret in `X-Astro-Receipt`, never in a URL. Save only its digest, bound to request ID, operation type and expiry, in the accepted-record transaction. `Store.hold` now verifies the receipt **before** comparing retry content or returning the frozen internal row. Only explicitly limited status fields cross a public route; never expose that internal row as a public DTO.
3. Initial creation still requires a valid purpose/email-bound verification token. Consume it only in the successful save/hold transaction. An unchanged retry with the matching receipt can retrieve the original outcome without consuming a second token; changed content returns a conflict. A different receipt cannot claim an existing request ID.
4. Status returns only the permitted summary: reference, service/quantity/fee, date/time, payment/appointment/link state and verified Meet URL when ready. No birth notes, provider payloads or private client notes. Inquiry receipts reveal “saved/not confirmed” and reference, not a searchable inbox. Bound status polling and response size.
5. An active checkout's receipt expires no later than appointment end +24 hours; inquiry receipt access uses a proposed 24-hour limit. Before a hold exists, it has no authority. Server-side expiry/revocation applies even if the tab remains open. A short public reference may be printed in mail; it is never the receipt secret.
6. After closing a tab or changing devices, “Check my appointment” accepts the public reference and email, then fresh purpose-bound verification for **that single booking**. Add `booking-status` as a distinct purpose and bind the challenge/grant to the reference. Use generic lookup responses and independent rate limits to prevent email/booking enumeration. Do not create a general “list all bookings for this email” endpoint. An expired browser receipt is recoverable through this path, not by weakening authentication.

OTP remains six digits, five minutes, bounded guesses/resends and a one-use action proof. Migration 003 renamed the challenge `delivered` flag to `send_accepted`: provider acceptance is not inbox delivery. A received code can prove mailbox access even if later delivery reporting is delayed, provided its safe acceptance state was recorded. If sending or recording the result is uncertain, give a clear retry path; never queue an old code for later bulk delivery. Codes stay off the general delivery queue. The locally checked `resend_email.py` sends after commit, uses the saved challenge UUID as its idempotency identity, rejects redirects/malformed success responses and only allows the still-current, unexpired challenge to be marked accepted. It has one attempt and a ten-second socket timeout within the host's request ceiling, not an unbounded retry loop. Public sending-domain DNS is observed and verification is user-reported; protected key/configuration and real delivery proof remain pending. Returned email references are now persisted for signed-event correlation.

If a verification response is lost after its token was created, do not reuse a consumed code by weakening the check: a new code is acceptable, with details preserved and a clear explanation. If a save response is lost, first recover that same receipt rather than request another OTP or silently submit again. Editing the email invalidates verification. Do not allow a delayed response from an old modal, tab or service selection to submit a new payload.

Abuse controls cover code sends, verification attempts, receipt recovery, order creation and status reads. Keep database-backed limits across instances. Engineering default: at most one active checkout hold per verified email, with a “Resume your current payment” response, not a second simultaneous hold; another appointment is possible after the first checkout finishes/expires. Rate limits are not proof of identity. Add a new challenge provider only for measured abuse and explicit approval, not by default.

Add atomic account-wide/per-purpose send budgets as well as per-email/IP limits; concurrent requests must not all spend the last available allowance. Reserve measured headroom for already accepted obligations and count uncertain sends conservatively. Use shared account scope across test/live where the provider shares quotas. Unknown quota/readiness never grants verification. A “resume” hint cannot reveal another checkout's details: require its receipt or C03's single-booking verified recovery. Bound expired-limit cleanup batches and stored keys so abuse cannot itself exhaust database storage.

## C04 — Payment handling is a small, explicit state machine

**2026-09-11 C03/C07/C08 checkpoint:** The user confirms the Resend team currently serves only this website. Known daily/monthly quota refusals wait at least one day without spending delivery attempts, provided there was no earlier uncertain send. Unknown sends retain the 24-hour idempotency boundary. Monthly reset is not guessed; recovery follows actual provider acceptance. Signed raw-body Resend events and minimal OTP provider references are now persisted and deduplicated. Inquiry source/seen fields and authenticated inquiry/attention views are implemented. These are locally verified capabilities, not live email/login proof. Payment and meeting exceptions remain unfinished; the private attention view presently covers inquiry emails only.

Keep booking, order, payment and delivery states separate. A failed second payment must not destroy an earlier accepted appointment; a refund must not silently release a slot. Proposed order states are `preparing`, `ready`, `creation_unknown`, `failed`; existing booking states remain `held`, `confirmed`, `expired`, `cancelled`, `payment_review`. Store exceptions independently so a confirmed/cancelled booking can still have a payment problem.

| Event | Required durable outcome | Customer result |
| --- | --- | --- |
| Verified request and free time | Freeze quote, create hold/claim and order intent atomically; prepare provider order outside lock | Preparing secure payment |
| Order created and bound | Store order ID, receipt, merchant/mode and amount before exposing checkout configuration | Pay the reviewed amount |
| Create-order response uncertain | Keep `creation_unknown`, receipt and original intent; reconcile, never blindly create another | Checking payment setup; no second pay action |
| Captured payment verified while own hold is valid | Record payment/event and confirm once in the schedule transaction; save delivery intent | Appointment confirmed; link may still be preparing |
| Authorization only or provider status unknown | Record pending status and continue bounded reconciliation | Payment being checked; do not pay again |
| Known failed attempt while order/hold still valid | Record failure; allow another attempt on the same order only after checking its current state | Payment was not completed; retry the same checkout |
| Hold expires, including while checkout is open | Release only its claim; no timer extension or stale confirm; keep order tracking | Time reservation expired; check payment status before starting again |
| Captured payment after expiry/start/cancellation, mismatched amount or extra payment | Persist money exception without seizing another claim or erasing existing confirmation | Payment received; appointment needs attention |
| Duplicate notification | Return its existing durable result, no second booking/job | No visible duplicate |
| Phone cancellation | Mark cancelled/release own claim/save update intent atomically; money history remains | Appointment cancelled; refund status stated separately |
| Refund/dispute notification | Update payment/exception facts, not the appointment schedule automatically | Reflect verified money state; client resolves terms separately |

Specific implementation obligations:

- Create the Razorpay order with an environment-distinct opaque receipt of at most 40 characters, integer INR paise and no partial payments. Never put birth data/notes in Razorpay metadata. Checkout may receive the public key ID and order ID; the key secret/webhook secret stay server-side. [Order API](https://razorpay.com/docs/api/orders/create/).
- Do not assume a generic idempotency header makes order creation repeat-safe. For uncertainty, retrieve by receipt, paginate and exact-match receipt, merchant environment, amount and internal binding; verify an individual matching order before adopting it. Zero results on one lookup do not prove creation failed; multiple matches need review. Prove provider behaviour in test mode before defining safe re-creation. [Order lookup](https://razorpay.com/docs/api/orders/fetch-all/).
- The normal request prepares its order after commit using a bounded provider call. Atomically record that the first external creation is about to start before sending it; a competing request cannot start another. If execution stops after this marker, lease expiry alone never permits another create call: reconcile the receipt because the old process/provider may still finish. If it stops before any external attempt, a conditional claimant may take over only while the hold is valid. Expired unattempted intent stays expired; no background creation of a newly payable order for an expired slot.
- A stale external order is not necessarily cancelled when the website hold expires. Do not pretend closing the payment window prevents a late charge. A fresh intent after expiry is explicit, never automatic; old orders remain reconciled and late captures enter review.
- Browser confirmation includes stored-order comparison and official signature verification, then a server fetch of payment capture/amount/currency/order. A signed provider notification is verified over original bytes and durably deduplicated by provider/environment/event ID. Use one finalization function for browser, notification and reconciliation paths.
- Valid notification data that arrives before local order binding must be retained as an unmatched event for reconciliation, not acknowledged and discarded or forced onto an arbitrary booking. Bound stored payloads and retain only needed fields/audit evidence. Invalid signatures do not write payment records.
- Verify against current persisted state inside the schedule lock. Provider event timestamps do not resurrect an expired/reassigned slot. If money moved during the hold but the first verified finalization arrives after expiry, it still requires review under the current policy; say this plainly rather than falsely promising confirmation.
- Reconciliation must run without the customer's browser. Razorpay's failed notification retries are finite; monitor disabled endpoints and use bounded authoritative payment lookups. [Webhook guidance](https://razorpay.com/docs/webhooks/best-practices/).
- Do not rely on a 15-minute sweep to confirm a ten-minute hold. Normal browser/webhook finalization is prompt; schedule bounded delayed checks for only unresolved active orders (initial target 60 seconds, validated against provider limits). The sweep is rescue after dispatch failure. Keep explicit C04 late-capture review even if the customer paid before expiry but proof arrived afterwards; D06 must accept the customer-facing handling before live checkout. No refreshed deadline or hidden longer hold to mask this race.
- Refunds remain an authorized merchant process, not an automatic website button. Record verified refund references/amount/state and link them to the exception. “Seen” or a client note cannot turn a payment into verified/refunded. No invented tax invoice or cancellation/refund policy; D06 owns those decisions.

## C05 — One reliable delivery mechanism, not an orchestration platform

Extend `delivery_jobs`, not a second competing queue store. Each job has a record/type/version, recipient role, `next_attempt_at`, bounded attempt count, lease token/expiry, safe last-error code, provider reference and terminal outcome. Use unique purpose/version/recipient dedupe keys. Maintain a small result record per email/calendar operation where a single job has multiple outcomes.

2026-09-11 partial implementation: inquiry recipient jobs, frozen message processing, post-commit queue publication and separate publication acknowledgements/claims now exist. A fixed-destination Cloudflare consumer and independently authenticated recovery route are checked locally, with migration 006 applied permanently. Hosted execution, shared quotas, signed delivery events, private inquiry/attention access and proactive monitoring remain open. Failed queue retention/publication cannot erase SQL work; prior uncertainty still prohibits blind email replay beyond Resend's dedupe window. The 15-minute recovery schedule plus a 90-second live claim yields up to 16.5 minutes before one bounded run for a one-batch backlog; this is not prompt booking finalization or a completion guarantee.

- Commit job intent with the booking/inquiry. Publish a task carrying only job ID/environment after commit. Persist dispatch acknowledgement. A crash before/after task creation must be safe; provider task names alone are not permanent deduplication.
- One worker claims a due job using a conditional update/row lock and a bounded lease, releases the transaction, then calls the provider. All writebacks compare the lease token and record version; an old worker cannot overwrite a newer result. If the external result arrived after cancellation or lease loss, preserve its provider reference for reconciliation and do not mark the newer work complete.
- Python publishes saved opaque job IDs through Cloudflare's official queue API with a scoped server credential. One small Free Worker consumes queue bindings and uses fixed environment-specific Python handler destinations. Keep business/provider logic in the existing FastAPI application. Authenticate HTTPS handler calls with separate delivery/recovery server credentials, constant-time comparison and a documented rotation procedure; no public URL secrets, arbitrary task destinations or Google task-identity assumption. The helper's authority is limited to invoking existing due work, not editing prices/bookings or supplying payment facts.
- An ACK requires a structured, durably recorded result for the expected job/environment. Generic HTTP 200, HTML preview-login pages, redirects, ambiguous timeout or wrong IDs do not complete a job. Valid no-op duplicates return a matching terminal result; missing/transient work remains recoverable. Distinguish queue HTTP-publish acceptance from handler completion, and prove response-loss on both boundaries.
- Retry temporary failures with backoff and a maximum number/age, but retain terminal failures visibly. Honour provider rate limits. A poisoned job cannot monopolize the queue; batch recovery queries are bounded and indexed. Do not spin, sleep for minutes inside a request, or use an in-process background task as durable storage.
- Fix duplicate/uncertain external calls with provider identity and state, not just leases: a provider may act before a crash. Stable event IDs and email idempotency keys matter even with one worker. Uncertain email results beyond the provider's dedupe window require review, not blind replay.
- Recommend a **15-minute independent safety sweep**, subject to D03/D07. Cloudflare Free Cron invokes a bounded Hobby-capable Python recovery handler; normal dispatch is immediate through Free Queues. No Vercel Pro Cron, browser timer or keep-awake loop. Saved Neon jobs outlive free queue retention; recover missing publication/expired leases, not all historical work. Test zero visitors, queue loss/expiry, failed sweep and an alert independent of Resend. Independence is from visits/dispatch, not from hosting availability.
- Recovery must inspect due pending jobs, expired leases, missing dispatch acknowledgement and unresolved order/payment creation. It must not sweep/re-send every historic confirmation. Stop new checkout when required delivery is known broken; continue processing already accepted obligations.
- Reconcile booking/payment/cancellation state before post-outage dispatch. If a session has already started, suppress obsolete upcoming-session confirmations and create an operator-visible unmet-obligation result, not a backdated appointment. Keep accepted provider references for repair. Measure the helper's CPU/requests, queue operations and every Python attempt against Free/Hobby limits; bounded retries cannot depend on Pro's longer runtime.

## C06 — Google connection and meetings are distinct from sign-in

Client Google sign-in grants private-page access only. Put one “Connect Google Calendar”/“Reconnect Google Calendar” control in a quiet connection area, restricted to the pinned client identity; customers never grant Calendar access. No additional client password database.

- Calendar authorization uses a short-lived single-use state record bound to the signed-in client, exact redirect URI, requested scope and separate browser correlation. Revalidate pinned Google identity when connecting; signing into a different Google account must not attach its calendar. Do not overwrite a working refresh token if a later response omits one; serialize token refresh/update and handle revocation without leaking tokens.
- The app uses `HashRouter`; Google callbacks cannot live in the URL fragment. Use a real backend `/api/.../callback` URL, then redirect to the private page without codes/tokens in the fragment. Current admin cookies are `SameSite=Strict`; a cross-site callback must not assume that cookie arrives. Use a separate short-lived `SameSite=Lax` correlation cookie for the top-level GET callback, tied to the server-side state and still-valid original admin session. Preserve Strict cookies and CSRF checks for normal admin writes. Test mismatch, replay, expired/revoked original session, denied consent, duplicate tabs and proxy redirects. [Cookie behaviour](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie).
- Pin an explicitly chosen client-owned booking calendar and test its Meet capability. Start with the minimum supported Calendar scope for that calendar/operation. Record whether external-app publishing/verification is required; development consent expiry is not a sustainable production setup. No service-account impersonation or alternate meeting provider fallback.
- Test a customer using a non-Gmail email address and the actual browser/phone joining path, including host admission where required. Booking does not require a Google account by assumption. If the chosen Meet configuration imposes a sign-in/admission requirement, disclose it before payment and obtain the account-capability decision; do not claim every guest can join without verification.
- Persist the intended Google event ID before insert; encode it in Google's permitted format. Also persist a unique conference-request ID per booking. On uncertain insert, fetch that event ID; do not generate a fresh event/Meet for the same booking. Send minimal event text and private visibility where supported; no birth notes or unrelated guests. [Event creation and identifiers](https://developers.google.com/workspace/calendar/api/guides/create-events).
- Model conference creation as pending/ready/failed. Retry/check the same event until its verified Meet link is ready or the retry limit is reached. Do not email a fabricated or empty link. Record invitation request state separately from conference readiness and email outcome. The organizer receives the website confirmation; the customer receives Google's calendar invitation plus the website confirmation. This is intentional, not two competing bookings.
- Re-read booking version before an event mutation and after provider completion. Cancellation that races event creation must converge on a cancelled event; it cannot promise that no obsolete email was ever accepted in flight. A corrective cancellation message remains necessary. Deletion failures stay visible and retryable.
- The website database is the booking authority. Google is a meeting/calendar output, not an additional scheduling input. Moving/deleting an event in Google must not silently move/cancel a website appointment. No automatic two-way calendar sync, personal-calendar busy import, rescheduling or attendance/no-show tracking in this scope. Explain this during handover and surface missing/changed application-owned events in bounded reconciliation.

## C07 — Inquiries and notifications have clear destinations

| Trigger | Customer sees / receives | Client receives / sees | What it does not do |
| --- | --- | --- | --- |
| Email verification | Code at the entered address; clear expiry/resend | Nothing | No appointment, inquiry or Calendar event yet |
| Home consultation request or Contact form accepted | Saved reference and one acknowledgement | One notification at `astroadvicebyks@gmail.com`; protected inquiry record | No payment, reserved time or promise of an appointment |
| Prashna inquiry accepted | Saved reference/acknowledgement, clearly an inquiry | Question/location/contact record and one notification | Not a paid question or automatically purchased consultation |

- Use explicit `source=home/contact/prashna` and optional validated service ID in inquiry records. Existing Home and Contact share `kind=contact`; preserve verification purpose while adding source attribution. Never infer trusted routing/recipients from a browser-supplied address.
